# NarutoLauncher v25: зіставлення трьох аудитів ОЗУ

09.11.2026. Координатор Codex зіставив власний попередньо завершений аудит,
незалежний звіт Claude та уточнений незалежний звіт Antigravity. Оптимізації
продукту не реалізовувались. Оновлення v25 стосується лише адаптивного дока;
воно встановлене на Home LenovoTV, що перевірено до початку аудитів.

## Що перевірено

- **Codex:** поточний JS/CSS/Java, реальні геометрія й screenshot Lenovo,
  розміри растрових файлів/PCM, процесно атрибутований meminfo на пристрої.
- **Antigravity:** незалежне читання JS/Java, перевірка 29 freeze-хешів,
  аналіз наявних raw meminfo. Без власного A/B і без взаємодії з Lenovo.
- **Claude:** незалежне читання, ті самі device-evidence, 21 локальний
  Chromium-прогін із disposable профілями, runtime-експериментами та GC.
  Це Windows private bytes / окремий GPU-процес, НЕ Android PSS.
- Обидва агенти не читали інші рев’ю перед завершенням власного.
  Координатор вимагав виправити фактичні помилки й надмірну точність прогнозів.
  Висновки нижче спираються на виправлені звіти, не на початковий worker summary.
- Product freeze залишився 29/29. Усі візуальні ресурси й попередні правки
  звуку збережено. Нових записів у Lenovo під час агентських аудитів не було.

## Реальні цифри Lenovo

Враховано host ua.konoha.tv та лише його sandbox renderer за packageList.
Кожен стан — 3 вибірки. CDP був приєднаний. Сцена Team 7, Gamabunta,
п’ять обраних + архів; audio=true, ambience=false. AudioContext ще не створено.

| Стан | PSS разом, МіБ | Діапазон |
|---|---:|---:|
| Home до гри | 299.90 | 299.14–301.04 |
| Гра відкрита, забіг не починався | 321.12 | 319.52–322.11 |
| Home одразу після закриття гри | 323.39 | 323.09–323.64 |

Дельта після гри: **+23.50 МіБ**, за одним циклом і коротким інтервалом.
Це не доведений накопичувальний витік і не гарантовано повернена економія.
Chromium/Skia/GC можуть звільняти cache пізніше або під тиском.
Попередні ~208 МіБ v23 не є порівняльним baseline цього тесту: інші кеші,
стан прогріву, техніка та debugger. Причинності «v25 додала 92 МіБ» не встановлено.

## Порівняння висновків

| Напрямок | Codex до порівняння | Claude | Antigravity, уточнений | Висновок координатора |
|---|---|---|---|---|
| Приховані панелі/гра | Retained canvas, не доведений leak | Те саме + local panel/GPU докази | Зняв P0, підтвердив hidden canvas | Перший пріоритет: очистити панель і release Canvas після unmount |
| Аудіокеш | PCM без бюджету, ~22 МіБ за 2 старі треки | Евікція дала 23–25 МіБ renderer на ПК | Погоджується з PCM-моделлю | Найпередбачуваніший резерв, коли музика використовується |
| 18 декодів шпалер | Великий raw/startup budget | Нема стабільної steady-state різниці на ПК | 10–15 МіБ PSS як гіпотеза | Корисно для старту; не обіцяти конкретної економії Home PSS |
| 11 ефектів | Сильний raw резерв, тільки 2 пози потрібні жабі | Lazy-effects без стабільної різниці renderer | 5–9 МіБ PSS як гіпотеза | Дозавантажувати активне; реальний PSS невідомий |
| Іконки | Runtime-size variants за DPR | Погоджується, PSS невідомий | Окремої оцінки немає | Малий ризик, чіткий pixel budget, не гарантована PSS дельта |
| Атласи гри | Тільки герой + менші клітинки | Погоджується | Погоджується | Окремий runtime-набір, без зміни фізики/малюнків-оригіналів |
| Fullscreen Canvas | Обмеження площі / trim у фоні | Local GPU зменшується, великий розкид | Помірний ризик об’єднання | Спочатку release у фоні; не зливати різні шари заради кількох МіБ |
| CPU home під панеллю | Окремо від RAM | 60 style recalc/с на ПК | Спеціального perf-тесту немає | Зупиняти декоративний цикл під панелями, залишити потрібні прев’ю |

Моя початкова ціль **−30…−60 МіБ Home PSS** була гіпотезою до незалежних
експериментів. Після порівняння вона **не прийнята як прогноз** для поточного
Home без музики: локальний A/B не підтвердив очікуваний steady-state ефект
lazy scenes/effects. Це не спростовує користь для старту й GPU; її треба
виміряти іншим сценарієм на Lenovo.

## Що покращити й на скільки

**Нема жодного виміряного optimized-build PSS на Lenovo.** Числа нижче мають
різні типи доказів; їх не можна складати як гарантований результат.

| Пріоритет / зміна | Кількісний орієнтир | Що це за число / обмеження |
|---|---|---|
| 1. `app.js:141` / `runner.js:101–104`: очищати `#panel-content`, обнуляти Canvas після unmount | **10–20 МіБ PSS після гри — оцінка**, не виміряна економія | Lenovo показав +23.5 МіБ після циклу; retained runner-canvas має 2.64 МіБ raw. Desktop release дав ще 7–9 МіБ GPU після закриття, але не Lenovo |
| 2. `audio.js:24–26,60–77`: LRU/eviction неактивних треків і cues | **~11 МіБ PCM за кожен трек; ~22 МіБ за два** | При 48 kHz. ПК: два старі треки −23…−25 МіБ renderer; для поточного TV audio cache=0, виграш тут зараз 0 |
| 3. `app.js:148`: окремі thumbnails сцен + lazy loading | **142.38→8.90 МіБ raw** для 18 карток 480×270 | **−133.48 МіБ pixel budget**, НЕ прогноз PSS. Прихована галерея теж має очищатися; не додавати сюди вдруге виграш рядка 1 |
| 4. `icons.js`: 256/384/640 варіанти за фізичним розміром | **−7.875 МіБ raw** для 6 іконок 640→256; до **−26.25 МіБ raw** для всіх 20 | Взаємно включені сценарії; 4K може потребувати 384/640. Оригінали зберегти, реальний PSS невідомий |
| 5. `technique-art.js:9–14`: малюнки лише активної техніки, обмежений кеш | **−20.25 МіБ raw**: 11→2 при Gamabunta | 2 пози жаби лишаються; plate Chidori взагалі не потрібен для процедурної анімації. Малюнки 768→384 додатково зменшують raw budget, але перевірити чіткість |
| 6. `runner.js:39–41` / `runner-art.js`: тільки активний герой, cell512→256 | **−12 МіБ raw** від вибору героя АБО до **−18 МіБ raw** від зменшення 4 атласів | Два способи перетинаються; не додавати 12+18. Стосується гри, не першого Home до відкриття гри |
| 7. `app.js:288,330`: release Canvas у фоні з відновленням на resume | **7.99 МіБ raw** для двох поточних fullscreen Canvas | GPU/композитор може мати інші копії; у Lenovo Graphics=0, економія PSS невідома. Об’єднання Canvas не потрібне для першого кроку |
| 8. `app.js:316–325`: пауза декоративного циклу під модалками; парaлакс scoped до `.village` | На ПК **~60 style recalc/с** від home-циклу | Це передусім CPU/GPU; не продавати як десятки МіБ RAM. Perf-порівняння гри було частково змішане з game-over |

Спочатку lifecycle панелей + аудіокеш. Це можна перевірити без зміни
затвердженого стилю, розмірів ефектів або якості шпалер. Потім runtime-варіанти
іконок/атласів і thumbnails. Оригінальні ресурси не видаляти.

Зупинка AudioContext у фоні — окрема симетрична pause/resume зміна; suspend
сам по собі не видаляє PCM cache. Не евіктити confirm, який ще звучить,
зберегти pinned активні focus/confirm, sample-clock overlap музики,
`onended` перед native launch та миттєвий launch при prefs.audio=false.

## Спільна оцінка без подвійного підрахунку

- **Поточний Home без музики:** доказової сумарної цифри немає; для планування
  лише обережна гіпотеза **0–10 МіБ PSS**, плюс невиміряні GPU/піки старту.
- **Home після гри:** гіпотеза **10–20 МіБ PSS** із cleanup; приблизно 3–6%
  від виміряних 323.4 МіБ. Верхній орієнтир спостереженої дельти — 23.5 МіБ.
- **Після перемикання трьох музичних треків:** два старі буфери — **~22 МіБ
  PCM**; додатковий потенціал FX LRU залежить від кількості прослуханих технік.
- **Гра + використання кількох треків:** сценарний орієнтир **20–40 МіБ PSS**
  економії після першого етапу, **не обіцянка для Lenovo**. Базовий Home-замір
  був без музики, тому не віднімати це автоматично від 300 МіБ.
- Ефекти, thumbnails, старі фони й кеші можуть перекриватися. Великі desktop
  GPU-дельти не додаються до TV PSS і не переносяться на пристрій як прогноз.
- Скорочення APK, CSS чи JS bundle не еквівалентне зменшенню ОЗУ. Фіксованої
  нижньої межі PSS для WebView за цими даними не встановлено.

## Як підтвердити при наступній реалізації

Одна зміна за раз; однакові prefs, сцена/техніка/6 карток, WebView version,
foreground/background, температура й режим debugger. A/B на свіжих процесах
з однаковим warm-up, мінімум 3 запуски кожного варіанта. Home, галерея сцен,
техніки, гра: 5 циклів відкриття/закриття, samples через 10 і 60 с, щоб
відділити дрейф від накопичення. Аудіо — окремий сценарій із трьома треками.

Сумувати PSS лише процесів цього пакета; окремо RSS/SwapPSS, private dirty,
доступну graphics/dmabuf статистику та frame-time. Graphics=0 не означає
відсутність GPU-пам’яті. Не примушувати memory pressure на користувацькому TV
без окремого погодженого діагностичного сценарію.

Регресійні перевірки: повторне відкриття панелей, збережені обрані/порядок,
перший кадр/ротація, стрибки Гамабунти, біг/підкат обох героїв, повна репліка
на OK, mute → негайний запуск, Back/repeated OK, повернення Home й музики.
Нативний rewrite чи заміна всього плеєра для цього не потрібні.
