# Незалежне рев’ю ОЗУ — Codex / v25

09.11.2026, до отримання висновків інших агентів. Product-код після встановлення
v25 не змінювався. Перевірено frontend, Android bridge, життєвий цикл, актуальний
APK manifest, розміри всіх растрових ресурсів та реальні PSS на Lenovo.

## Виміряні факти

`revisions/v25/device/memory/` містить dumpsys meminfo для кожного PID та три
вибірки кожного стану. До суми входять лише ua.konoha.tv і пов’язаний renderer
WebView, встановлений через packageList у dumpsys activity processes.

| Стан | PSS, МіБ (середнє; діапазон) |
|---|---|
| Головний екран, Team 7 / Gamabunta | 299.90; 299.14–301.04 |
| Відкрита гра, без початку забігу | 321.12; 319.52–322.11 |
| Одразу після закриття гри | 323.39; 323.09–323.64 |

Під час вимірювання CDP був приєднаний; процеси прогріті після нового запуску.
Аудіоконтекст ще не створено, audio cache=0. Це не замір із музикою. Закриття
гри не повернуло пам’ять негайно; це НЕ доказ витоку: GC, browser image cache,
Skia/GPU та алокатор можуть відкладати звільнення. У фіналі prefs і HOME збережено,
гра закрита, екран Awake. Порівнювати ці 300 МіБ з попередніми 208 МіБ як
регресію v25 некоректно: інші прогрів, техніка, стан кешів і підключення debugger.

Всі нижчі числа pixel/PCM budget є розрахунками одного представлення ресурсу,
а НЕ вже виміряною економією PSS. Browser може вивантажувати decoded pixels,
зберігати кілька CPU/GPU-копій або не повертати сторінки ОС відразу.

## 1. Ефекти: завантаження всіх малюнків замість активного

`prototype/technique-art.js:9–14` безумовно створює та зберігає Image для 11
ресурсів. У живому UI artStatus підтвердив усі 11 decoded=true. Кожен 768×768:
2.25 МіБ RGBA, разом **24.75 МіБ**. Chidori plate теж завантажується, хоча
`api.draw` одразу обирає процедурне малювання і цей plate не використовує.

Рекомендація: завантаження активної техніки, дві пози жаби для Gamabunta,
обмежений LRU для нещодавніх; галерея дозавантажує лише видимі прев’ю.
Окремі 384/768 варіанти відповідно до фізичного розміру та DPR.
Для нинішньої жаби 11→2 дає **20.25 МіБ** меншого RGBA budget; два 384px
малюнки замість всіх 11×768 дають **23.625 МіБ**. Це сильний перший кандидат.
Не ламати api.ready, нерухомий перший кадр і перемикання технік до завершення decode.

## 2. Шпалери: загальне decode на старті й повнорозмірні галереї

`prototype/app.js:74–82,335`: запускаються decode усіх 18 сцен, разом
1920×1080×4×18 = **142.38 МіБ** RGBA budget. `decodedScenes` зберігає
Promise<void>, не Image: не можна називати його гарантованим витоком 142 МіБ.
Ці predecode nevertheless створюють непотрібний стартовий тиск і прогрівають кеш.
`scenesPanel` використовує ті самі повні JPEG для маленьких карток.

Рекомендація: активна + наступна сцена; скасування непотрібних queued decode;
окремі 480×270 thumbnails, lazy loading. Дві background-шари потрібні для fade,
але після fade старий backgroundImage можна прибирати з перевіркою sceneVersion.
18 thumbnails 480×270: **8.90 МіБ** проти 142.38, різниця **133.48 МіБ** raw
budget для галереї. **Не обіцяти повернення 133 МіБ PSS**: частина сцен уже може
бути вивантажена Chromium. Потребує A/B на свіжих процесах, однаковій сцені.
Зберегти оригінали; не зменшувати TV-шпалери без вибору за фізичним екраном.

## 3. Іконки завеликі для розміру відображення

20 themed icons 640×640, **31.25 МіБ** raw budget, але на головному зараз видно
лише 6. 256px варіанти: 0.25 МіБ/іконку, економія **7.875 МіБ для шести**
або **26.25 МіБ для всіх двадцяти**. 384px варіанти дають 1 МіБ/іконку економії.
Потрібно обирати 256/384/640 за CSS-size×DPR, щоб не погіршити великий TV.
`appCard` може додавати loading=lazy/decoding=async для бібліотеки, dock — eager.
Це не привід заміняти намальовані іконки системними.

## 4. Аудіо: кеш не має бюджету та не чиститься після перемикання/вимкнення

`prototype/audio.js:24–26,64–74`: Map утримує decoded AudioBuffer Promise;
stopMusic очищає активний this.buffer, але не cache. Три музичні прев’ю після
відвідування всіх — **32.98 МіБ** PCM при 48 kHz; досяжні ефекти + музика
разом **40.90 МіБ** (див. verification/audio-reachable.json). Частина focus-cue
не досяжна з UI, тому це ще й верхній file budget, не поточне навантаження.
Поточний аудіокеш=0 → **поточна економія тут 0**.

Рекомендація: PCM-бюджет LRU, активна музика + активні cues; після перемикання
відпускати старий трек. Дві непотрібні музики ≈**21.99 МіБ**; верхня економія
після активного перебору налаштувань близько **25–29 МіБ** PCM. Не чистити
буфер, який ще звучить, не псувати 3.5s overlap і v24 onended-before-launch.
Перехід на HTMLAudio streaming окремо ризикований для sample-clock crossfade;
для першого кроку достатньо обмежити cache без заміни плеєра.

## 5. Мінігра: всі атласи обох героїв і прихована сцена

`prototype/runner.js:39–41`: при mount завантажуються обидва герої, обидва
slide-atlas і background: **26.64 МіБ** raw. Зараз до першого відкриття гри
вони не завантажуються — це вже правильний lazy boundary.
Після закриття `app.js:141` приховує modal, але залишає #panel-content із
canvas 1280×540 (**2.64 МіБ** одного backing store). unmount припиняє rAF і
від’єднує слухачі; постійний timer leak у грі не підтверджений.

Рекомендація: атласи лише активного героя; cell512→256 у runtime-варіанті
(physics/collision без змін). Чотири атласи разом 24→6 МіБ: **18 МіБ** raw;
активна пара замість всіх чотирьох — **12 МіБ**, ці числа перетинаються.
При close очистити panel-content і обнулити великі canvas після unmount.
Реальний спостережений приріст відкриття гри **21.22 МіБ PSS**, не автоматична
гарантія такої самої економії оптимізації. Перевірити jump/slide, DPR і повернення.

## 6. Canvas/композитинг та фоновий стан

`app.js:288`: два fullscreen Canvas на Lenovo 1366×767 — **7.99 МіБ** одного
RGBA представлення разом. DPR capped=2 корисний. Віконний canvas лише навколо
активної іконки та trails зменшить бюджет technique-canvas приблизно на
**3–3.5 МіБ** на Lenovo; потребує правильного origin і запасу для стрибка жаби.
Зниження DPR частинок — **2–3 МіБ** цього бюджету, а не десятки МіБ.
Вимкнення rAF саме по собі не звільняє pixels.

Android onPause зупиняє JS/audio/game, але утримує WebView та кеші. Можливий
trim непотрібних кешів/Canvas при memory pressure, із симетричним resume.
Не викликати forceStopPackage, destroy/recreate WebView на кожний Home,
software rendering чи глобальні clearCache без A/B: повільне повернення і
ризик зламати звук перевищують непідтверджену економію.

## 7. CPU окремо від RAM

`app.js:307–310`: всі десять preview Canvas малюються кожен кадр; відсікання
невидимих карток зменшить CPU/GPU роботу й allocations, але не є доказом
значної постійної економії RAM. Три displacement Canvas 512² ≈3 МіБ;
замінювати 512 drawImage на shader для цієї задачі не виправдано без профілю.
R8/release build і об’єднання CSS не основний резерв: APK менший ≠ RAM менша.
Map із 13 ResolveInfo та 128px native icons із recycle уже невеликі й обмежені.

## Пріоритет і чесна оцінка

1. Ефекти on-demand + runtime-sized icons: приблизно **25–35 МіБ raw budget**
   на нинішньому Home, із збереженням стилю; PSS підтвердити після реалізації.
2. Шпалери/thumbnail/lazy policy: найбільший змінний резерв; **десятки МіБ**
   потенційно, але зараз недостатньо даних для чесного точного PSS прогнозу.
3. Audio LRU: до **~22 МіБ лише за рахунок двох старих треків**, нуль у
   нинішньому стані без audio context. Гра: **12–18 МіБ raw** під час гри.

Не додавати всі верхні межі: однакові pixels можуть уже входити до кількох
рядків, а browser/platform кеші не дорівнюють PSS. Орієнтир першого A/B —
**мінус 30–60 МіБ Home PSS**, не обіцянка. Після lazy wallpapers можливий
більший виграш; заявляти кінцеві 100/150 МіБ без вимірювання зарано.
Нативний rewrite не потрібен для перевірки цих резервів.

Наступний implementation gate: одна оптимізація за раз, однакові settings,
свіжий процес і однаковий warm-up; Home→галерея→звук→гра→Home→інший app→Home;
PSS/RSS/SwapPSS усіх пов’язаних процесів, frame-time, скриншоти, повна репліка,
mute-immediate-launch та Home-повернення. Спершу погоджений код, потім build,
окремо дозволене оновлення пристрою.

Методика: [Android dumpsys](https://developer.android.com/tools/dumpsys),
[bitmap size](https://developer.android.com/topic/performance/memory/guide/bitmaps),
[AudioBuffer PCM](https://developer.mozilla.org/en-US/docs/Web/API/AudioBuffer).
